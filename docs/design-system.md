# 管理画面 UI 規則（デザインシステム）

出所: 2026-08-19 亥角さん「デザインルールみたいな、案件ごとのもの……あとは案件全ての案件共通のルール」
関連チケット: 【管理画面UX】UI規則（デザインシステム）を文章で書く――自動レビューの前提

## この文書の目的（＝自動レビューの前提）

「AIにシステム全体を見渡させて改善をチケット化する」を回すための**照らす規則**。
規則が無いまま自動レビューをすると「デフォルトのボタンが並んでてダサい」のような
**検証できない好みの表明**が大量に出てノイズになる。ここでは各規則を

- **違反を指させる粒度**（「美しく」のような語を使わない。数えられる／grep できる形にする）
- **実際に違反している現行コードの例つき**（file:line で示す。空論にしない）

で書く。**直すのは別チケット**。この文書は規則と違反一覧を出すところまで。

**規則は増やさない。** 今回は下記 4 項目のみ。5 番目以降は、人から指摘されたか
自動レビューで違反が現れてから足す（先回りして書かない）。

### 置き場所について（cc-pipeline core / products の整理）

この文書の規則は `btn-primary` / `.input` / `nav-badge` など **sido 実装に固有**の語彙で
書かれているため、コードと同じ sido リポジトリの `docs/` に置く（自動レビューは sido の
コードを見るのでここが参照される）。

- **全案件共通に昇格できるもの** = 規則 4 の「絵文字禁止・アイコン体系を使う」だけ。
  これは実装非依存なので、いずれ cc-pipeline `core` へ言い換えて移してよい。
- **この案件固有** = 残り全部。cc-pipeline `products/sido` からはこの文書を参照する形にする。

## 規則 1. ボタンの役割と見た目

### 1-a. 現状の棚卸し（まず事実）

ボタンのクラスは**共通コンポーネント／共通CSSが無く、各ページの scoped style で
その都度定義**されている。グローバル CSS（`apps/admin/src/style.css`）は 20 行で、
ボタン定義を一切持たない。結果、**同じ見た目のボタンが各ページで別々に再定義**されている。

実測（`apps/admin/src/pages`・`components`）:

- 使われている `btn-*` クラスは **40 種類以上**。多い順:
  `btn-cancel`(69) / `btn-save`(60) / `btn-edit`(55) / `btn-add`(52) / `btn-ghost`(50) /
  `btn-primary`(28) / `btn-del`(28) / `btn-order`(20) / `btn-link-sm`(19) / `btn-reject`(17) /
  `btn-ghost-sm`(17) / `btn-nav`(15) / `btn-toggle`(13) / `btn-delete`(13) …
- `.btn-primary` を**定義**しているファイルは 3 つだけ（`site-detail.vue` /
  `estimate-masters.vue` / `estimate-builder.vue`）なのに、**使用は 28 箇所**。
  → 定義のないページでは素の `<button>` に色が付かない、または別クラスで代用している。
- `btn-del`(28) と `btn-delete`(13) が**同義で併存**。`btn-cancel`(69) が
  「キャンセル」と「スキップ」と「副操作」の 3 役を兼ねている。

これが「役割ではなく成り行きで使い分けられている」の実体。

### 1-b. 規則（役割 → クラスの対応）

ボタンは**役割**で決める。役割は次の 4 つだけ。新しい `btn-*` を増やす前に、
下の 4 役のどれかで足りないかを必ず確認する。

| 役割 | 意味 | 使うクラス |
|---|---|---|
| 主操作 | その画面／モーダルで押してほしい 1 つ（保存・次へ・発行） | `btn-primary` |
| 副操作 | 任意・戻る・キャンセル・スキップ | `btn-cancel`（＝ghost 系）|
| 破壊的 | 削除・却下（元に戻せない／強い警告色） | `btn-del`（`btn-delete` は使わない）|
| 補助リンク | 一覧内の小さな導線（詳細へ・編集へ） | `btn-link-sm` / `btn-ghost-sm` |

**数えられる規則:**

- **1 つのフォーム／モーダル／ウィザードのステップに、`btn-primary` は原則 1 つ。**
  2 つ以上あったら「どちらを押せばいいか」が決まっていない＝違反。
  （grep 目安: 1 つの `<form>`・`.modal`・`.wiz-actions` ブロック内に `btn-primary` が 2 回以上）
- **破壊は `btn-del` に統一**。`btn-delete` は新規に使わない（同義の重複を増やさない）。
- **副操作を主操作の色（primary）で出さない**。「キャンセルも保存も同じ青」は違反。

### 1-c. 違反している現行コードの例

- `btn-del`(28) と `btn-delete`(13) の**同義併存**。例: `pages/contractors.vue:165`
  は削除でない「×（添付を外す）」に `btn-del` を使い、他ページの実削除も同じ `btn-del`。
  → 「破壊的か否か」がクラスから読めない。
- `btn-cancel` が**スキップ**に流用されている: `pages/estimate-builder.vue:171,186,205,232`
  （ウィザードのスキップボタンが全部 `btn-cancel`）。役割としては副操作で正しいが、
  クラス名が「キャンセル」なので**意味とクラス名がずれる**。
- `.btn-primary` 未定義ページでの primary 使用（定義は 3 ファイルのみ・使用は 28 箇所）。

## 規則 2. 空の状態（エンプティステート）

### 2-a. 規則

一覧やタブが空のとき、`class="empty"`（実測 70 箇所で使用）のメッセージには
**その場から押せるもの**を必ず置く。

- ✅ 空メッセージの中に、そのデータを作る**アクション**（`＋◯◯を追加`ボタン
  や、その場で開くモーダルの起動）がある。
- ❌ 「別の画面で登録してください」と**説明するだけ**で終わる（＝行き止まり）。
- ❌ 「別のタブから登録できます」と**別タブを案内するだけ**で、その場に操作が無い。

**数えられる規則:** `class="empty"` を含む要素のテキストに「〜してください」
「〜から登録」が出てくるのに、同じ空ブロック内に `<button>` も `<RouterLink>` も
無ければ違反（行き止まり）。

### 2-b. 満たしている例（規則どおり）

- `pages/process.vue:30` — 「まだ工程がありません。**「＋ 工程を追加」から登録してください。**」
  → 同画面に追加ボタンが実在し、その場で足せる。
- `pages/faq.vue:52` — 「FAQ がまだありません。**「＋ FAQ追加」から登録してください**」→ 同上。
- `pages/estimate-masters.vue:146` — 「まだ商社がありません。**「＋ 商社を追加」で登録できます**」
  → 同じ画面にインライン追加 UI がある。

### 2-c. 違反している現行コードの例

- `pages/estimate-masters.vue:92` — 「まだ単価が登録されていません。**「商社別単価」タブから
  登録・取込できます**」→ **別タブの案内だけ**で、この空ブロックにアクションが無い。
- `pages/purchase-orders.vue:79` — 「この業者に担当者が未登録です。**協力業者マスタで担当者
  （メール）を登録してください。**」→ テキストのみ・その場で担当者を足せない（行き止まり）。
- `pages/estimate-masters.vue:136` — 「商社は『協力業者』マスタの区分=商社
  （`<RouterLink to="/subcontractors">`協力業者`</RouterLink>`で登録）」
  → **別画面へのリンクだけ**（規則 3 とも重複違反）。

## 規則 3. マスタは使う場所の隣で直せる（既存 `master-editing-rules.md` の機械検査版）

規則そのものは `docs/design/master-editing-rules.md` に既にある（ページ遷移せずモーダル
で直す／追加した瞬間に反映／編集ボタンは使う場所の隣／消しても既存データは変えない）。
ここでは**違反を機械的に探せる形**に言い換える。

### 3-a. 機械検査できる違反条件

- **リンクだけ違反:** マスタを使う入力欄の近くで、`<RouterLink to="/{マスタ画面}">…で登録`
  のように**別画面リンクを出すだけ**で、同じ場所に**同じことができるモーダル起動が
  並んでいない**もの。対象マスタ画面 = `/contractors` `/subcontractors` `/estimate-masters`
  `/work-categories` `/vehicles` `/workers` `/settings` `/company-profile` `/schedule-categories`。
  （grep 目安: 上記 `to="/…"` の近傍に「で登録」「登録してください」があり、
  近くにモーダルを開く `@click` が無い）
- **例外（違反ではない）:** 印影登録のような**重い設定**は専用ページに残してよい
  （`master-editing-rules.md` 規則 1 の但し書き）。

### 3-b. 違反している現行コードの例

- `pages/estimate-masters.vue:136` — 商社の登録を `/subcontractors` への
  **リンクだけ**で案内。その場に「＋商社を追加」モーダルはあるのに、この文言は別画面へ誘導。
- `pages/purchase-orders.vue:79` — 担当者未登録を「協力業者マスタで登録してください」と
  **テキストのみ**で案内。発注書を作っている画面から担当者をその場で足せない。
- `pages/estimate-builder.vue:1193` — 「担当者が未登録です（`<RouterLink to="/contractors">`
  元請け業者マスタ`</RouterLink>`で登録）」→ 元請け本体の追加は R55 でモーダル化済みだが、
  **その担当者（連絡先）はリンクだけ**のまま。

### 3-c. 例外として正しい現行コード（違反にしない）

- `pages/estimate-builder.vue:1069` — 「印影など細かい設定は
  `<RouterLink to="/company-profile">`自社情報ページ`</RouterLink>`」
  → 印影は「重い設定」なので専用ページ導線でよい（規則 1 但し書きに合致）。

## 規則 4. 既にある暗黙ルールの明文化

人から繰り返し指摘されて既に守っている（＝好みでなく規則になっている）もの。

### 4-a. 絵文字は使わず Material Symbols アイコン（機械化済み）

- UI（`.vue` テンプレート）に**絵文字ピクトグラムを書かない**。アイコンは
  `<span class="material-symbols-rounded">icon_name</span>`（実測 88 箇所で使用）。
- **検査は既に自動化済み:** `node scripts/check-no-emoji.mjs`（絵文字があれば非ゼロ終了）。
  対象 = `apps/admin/src` と `apps/liff`。幾何記号（▲▼◯✓✕ 等）は許容。
- これは**唯一の全案件共通ルール候補**（実装非依存なので cc-pipeline core へ昇格可）。

### 4-b. 一覧の並びは 50 音順、現場は「元請け → 現場」の 2 階層

- 名前で並べる一覧は**読み仮名（かな）による 50 音順**。
  例: `pages/sites.vue:26`（並び替え「五十音」）・`:77`（`name_kana` を並びに使用）、
  `pages/reports.vue:763`（`localeCompare(b, 'ja')`）。
- 現場は**元請けとの 2 階層**で扱う（現場単独でなく元請けの下にぶら下げる）。
- **違反の目安:** 生成した選択肢配列を `.sort()`（引数なし＝コードポイント順）で
  並べている箇所（日本語は 50 音にならない）。`localeCompare(…, 'ja')` か
  かなキーで並べていなければ違反。

### 4-c. ステップ（ウィザード）のボタンは 戻る → スキップ → 次へ

- 複数ステップ UI のアクション列は、**進む向きに左から右へ「戻る → スキップ → 次へ」**。
  最初のステップは戻り先が無いので「戻る」を出さない。
- 準拠例: `pages/estimate-builder.vue:168-173`（コメントで規則を明記・2026-08-19）。
- **違反の目安:** ステップの `.wiz-actions` 等で「次へ／スキップ／戻る」の DOM 並び順が
  この順序になっていないもの。

## 付録: 現状の実装パターン（記述のみ・まだ規則ではない）

以下は観察された共通パターン。**まだ規則に昇格していない**（人からの指摘も自動レビューの
違反もまだ無いため）。「規則は増やさない」方針に従い、ここには**事実だけ**を記録する。
違反が現れたら、その時点で対応する規則へ格上げする。

- **入力欄 `.input`:** 多くのフォーム入力が `class="input"` を付ける（実測 20 ページで使用）。
  ただしボタン同様、`.input` の**定義が 19 ファイルに散在**（共通 CSS なし）。
  → 見た目は揃っているが、変更は全ページに手を入れる必要がある。
- **モーダル構造:** `.modal-overlay`（背景・`@click.self` で閉じる、35 箇所）＞ `.modal`
  （本体、25 箇所。広い版は `.modal wide`）＞ ヘッダ（`.modal-head` / `.modal-title` /
  `.modal-close`）＞ 本文（`.modal-section` / `.modal-body`）＞ `.modal-actions`
  （下部ボタン列、30 箇所）。おおむね一貫。例: `pages/contractors.vue:30,31,73`。
- **通知バッジ `nav-badge`:** サイドナビの件数表示は `App.vue` の `.nav-badge`
  （日報編集の承認・現場未設定の紐付け・残業申請・チャット・有給付与・見積抽出完了・
  注文書受注待ち）。`v-if="count"` で 0 のとき出さない。
- **必須項目の表示（不統一・要注意）:** `class="req"`（4 箇所）と、ラベル／プレースホルダ内の
  素のテキスト「（必須）」（`pages/sites.vue:93`・`pages/workers.vue:296` 等）が**混在**。
  統一マーカーが無い。→ 将来ここは規則 5 の有力候補（違反が出たら格上げ）。
- **色・余白の傾向:** 背景 `#f5f5f5`・本文 `#111`（`style.css:3`）。モーダル遮蔽は
  `rgba(0,0,0,.4)`。ボタン間 gap は 12px（`.modal-actions`）。スマホ（≤768px）は
  `.table-wrap` を横スクロールに切替（`style.css:9-19`）。数値の共通トークン化はまだ無い。
- **i18n:** i18n フレームワークは**未導入**（`package.json` に依存なし・`$t()`/`useI18n`
  不使用）。文言は**日本語ハードコード**。単一テナント日本語運用のため、多言語要件が
  出るまで導入しない方針（＝現状は「日本語直書き」が既定で、これ自体は違反ではない）。
