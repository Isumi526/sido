# データの保持期間と削除の仕様

作成: 2026-08-31（契約対応④）
状態: **ドライラン（数えるだけ）まで実装済み。実削除は未実装。**

> 契約 別紙2 は「退職3年後・解約後にデータを復元不能に削除」と書いているが、
> 本体DBの保持期間経過データを削除する仕組みが無かった。この文書は
> 「何を・いつ・どう消すか」を先に決めておくためのもの。

## 1. いまできること

```bash
node --env-file=.env scripts/retention-dryrun.mjs            # 3年で試算・ローカル
node --env-file=.env scripts/retention-dryrun.mjs --years 5  # 5年で試算
node --env-file=.env scripts/retention-dryrun.mjs --prod     # 本番を読む（読み取りのみ）
node --env-file=.env scripts/retention-dryrun.mjs --csv out.csv
```

**このスクリプトは1行も削除しない。** 保持期間を過ぎた「候補」を数えて出すだけ。
保持期間の確定値がまだ無いので、期間をパラメータにして試算できるようにしてある。
候補の件数が見えてから期間を決めるほうが判断しやすい。

**2026-08-31 時点の本番の候補件数: 全種別0件**（サービス開始から3年経っていないため）。

## 2. 何を・いつから数えるか

起点は種類ごとに違う。ここを間違えると「まだ必要な記録を消す」か「いつまでも消えない」になる。

| 種別 | 起点 | 理由 |
|---|---|---|
| 日報 | 日報の対象日 | 労基法109条の保存対象。作成日ではなく記録の日付 |
| 出退勤の打刻 | 打刻日時 | 同上 |
| 残業申請 | 対象日 | 申請日ではなく対象の勤務日 |
| 個人経費 | 支出日 | |
| 有給の付与 | **失効日** | 付与日を起点にすると、まだ使える有給を消してしまう |
| 現場チャット | 投稿日時 | |
| 退職した作業員 | **退職日** | ★下記のとおり、いま判定できない |

## 3. ★実装を進める前に決めること

### (1) 退職日を記録していない
契約は「退職3年後に削除」と書いているが、`workers` に**退職日を持つ列が無い**。
`status` / `active` で「退職済み」かは分かるが、**いつ退職したか**が分からない。

→ 退職日の列を足さないと、この条件は判定できない。足す場合、既存の退職者の
   退職日は遡って入れられない（記録が無い）ので、運用開始日からの適用になる。

### (2) 契約の3年と法定保存期間の関係
労基法109条は日報・賃金台帳などに**5年（当面3年）**の保存義務がある。
契約の「3年」で消すと、**法令上まだ保存が要る記録を消してしまう可能性**がある。

→ 保持期間の確定値は、契約と法令の両方を見て決める必要がある。
   確定するまで実削除は実装しない。

### (3) 消すのか、読めなくするのか
「復元不能に削除」は物理削除を指すが、法定保存義務と両立させるなら
「保存はするが通常の画面からは見えなくする」形もあり得る。契約文言の意図を確認する。

## 4. 実削除を作る時の決まりごと（先に書いておく）

- **人の承認ゲートを必ず挟む。** 自動で即削除にしない。削除は不可逆。
- **削除ログを残す。** いつ・誰の承認で・何を何件消したか。
  ログ自体は削除対象に含めない（消した記録まで消えると監査できない）。
- **テナントを跨がない。** 必ず `account_id` で絞る。
- **ドライランと同じ条件で消す。** 候補を数えるSQLと削除するSQLが別々に育つと、
  「見せた候補と違うものを消す」が起きる。同じ条件式を共有すること。
- **添付ファイルも一緒に消す。** DBの行だけ消してストレージに残ると、
  「消したはずの領収書が残っている」になる。
